# Анализ оптимальности технологического выбора

## Идея

Периодно (или по мере роста проекта) проводить ревью технологий, выбранных
для проекта/подсистем, на предмет оптимальности: не было ли более подходящего
стека под текущие цели, требования и команду.

## Мотивация

Технология выбирается один раз под контекст начала проекта, но проект живёт
и меняется: растёт команда, появляются новые требования (производительность,
сопровождаемость, найм, скорость фич), накапливается tech debt. Выбор,
оптимальный на старте, со временем может стать тормозом — или наоборот,
миграция может оказаться неоправданно дорогой. Без явного ревью такие
вопросы обычно поднимаются фрагментарно и эмоционально.

Пример вопроса: виртуальная камера написана на C++ (Media Foundation, COM) —
это оправдано (in-proc COM DLL, frame-пайплайн, интеграция с MF), или
часть компонентов (host, tray, CLI, UI-логика) можно было бы вести на .NET
как более популярном и продуктивном в разработке стеке (часть UI и так на
C# WinForms)?

## Что анализировать

- **Критерии**: соответствие целям (latency, память, интеграция с OS/COM/MF),
  стоимость изменений, наличие экспертизы/найма, экосистема и поддержка,
  риски vendor-lock / end-of-life.
- **Объекты**: каждый крупный компонент отдельно (MediaSource.dll,
  ProducerCore, tray-хост, CLI, UI, тесты), а не проект целиком —
  разбиение по границам ответственности (`IFrameSource`, shm-контракт)
  уже задано.
- **Альтернативы**: .NET (C++/CLI, P/Invoke, csproj-обвязка), Rust,
  оставить C++ — с честной оценкой стоимости миграции и рисков регрессий.
- **Формат**: документ-сравнение (таблица критериев) + вывод по каждому
  компоненту: «оставить», «пересмотреть при следующей крупной фиче»,
  «план миграции».

## Возможная реализация

- [ ] Инвентаризация компонентов: где C++, где C#, где PowerShell, границы
      и точки интеграции (pipe, shm, COM, task scheduler).
- [ ] Список критериев и весов (согласовать с владельцем проекта).
- [ ] По каждому компоненту — альтернативы и rough-оценка миграции
      (дни/недели, регрессионные риски, что ломает e2e).
- [ ] Сводный документ с рекомендациями; приоритеты учитывать в
      `pipeline-first.md` / `regression-safety.md`.
